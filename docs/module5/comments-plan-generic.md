# Generic Comments Feature Plan

This baseline was intentionally written without relying on the Task Tracker
repository structure. File names, storage technology, frontend framework, and
test conventions are treated as unknown.

## Data Model

A comment contains:

- `id`: string UUID generated by the server
- `task_id`: string reference to the parent task
- `author`: required string from 1 to 100 characters
- `body`: required string from 1 to 2000 characters
- `created_at`: UTC datetime generated by the server

Use separate request and response shapes. The create request should accept only
`author` and `body`; the server should derive the task reference from the route
and generate the identifier and timestamp. Trim author and body values before
rejecting blank content.

## API Routes

- `POST /tasks/{task_id}/comments`: create a comment and return HTTP 201.
- `GET /tasks/{task_id}/comments`: return the task's comments in a documented
  order.

Return HTTP 404 when the parent task does not exist and HTTP 422 when the input
violates the author or body contract. Editing and deletion should not be added
until ownership and product requirements are decided.

## Tests

- Create a valid comment and verify generated fields.
- List comments for one task without returning comments for another task.
- Reject blank and overlong authors.
- Reject blank and overlong bodies.
- Return 404 for a missing parent task.
- Confirm server-generated identifiers are unique.
- Confirm timestamps are UTC and list ordering is stable.
- Test the chosen behavior when a parent task is deleted.

## Frontend Changes

Add a task-level comments view with an empty state, existing-comment list, and
a small form for author and body. Show loading, validation, submission, and API
error states. Refresh or append the list only after a successful create
response, and preserve keyboard and screen-reader usability.

## Migration or Data-shape Notes

If the application uses a relational database, add a comments table with a
task reference and decide the deletion rule. If it uses document or in-memory
storage, introduce a separate comment collection or an embedded comment list.
Existing task responses should remain compatible unless the product explicitly
requires comments to be embedded.

## Open Questions

1. Are comments immutable, or can they be edited and deleted?
2. Is `author` trusted client text, or should it come from an authenticated
   identity?
3. What happens to comments when a task is deleted?
4. Should comments be returned oldest-first or newest-first?
5. Should task-list responses include comments or only a comment count?
6. Is pagination needed, and if so, at what threshold?

## Assumptions this plan makes

- A nested task-comments API is acceptable.
- Create and list are the minimum feature scope.
- The parent task must exist before a comment is created or listed.
- The application has a place to store comments, but the storage type is
  unknown.
- The frontend can add a task-level interaction, but its structure is unknown.
- Authentication, authorization, deployment, and database choices are unknown.
